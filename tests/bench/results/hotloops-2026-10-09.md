# Runtime hot-loop campaign — 2026-10-09

This campaign covers all 42 Dream release workloads on macOS arm64 (Apple M3), with native
execution and Node 26.4.0 WebAssembly measured independently. LLVM is 22.1.8 and Binaryen is
133. The scalar control uses the preserved compiler and an archive of the original C runtime;
the SIMD control uses the new compiler with that same original runtime. Queue reuse is then
compared against the SIMD control on wasm and the original control on native.

Each process warms the complete fixture before ten measured passes. References contain ten
process starts; acceptance comparisons contain twenty paired starts with rotating arm order.
The gate bootstraps process-median ratios, with 4,000 resamples and a 95% interval. A speedup
requires an upper bound below 1.0. The independent regression threshold is 1.10; inconclusive
rows are not accepted. Instrumented runs never enter these comparisons. Local background-app
load is a limitation of this runner; builds and correctness probes finish before timing starts.
The initial five-pass trials are retained separately. A live fixture edit was detected by the
reference fingerprint; the final campaign uses `--benchmark target/hotloops/frozen-42.dream`.
The comparator reads that snapshot once and uses those exact bytes for every arm.

## Changes under evaluation

- **SIMD feature propagation:** the signature anchor, C guest units and wasm codegen now agree
  on SIMD128. Feature policy enters signature, runtime-bitcode and debug-object cache keys.
  This changes LLVM's target capabilities without adding alias, overflow or floating-point
  promises. Native target flags and optimization pipelines are unchanged.
- **Ready-queue storage:** up to 64 entries reuse per-thread storage. Larger bursts allocate
  ordinary nodes; timer and foreign-completion nodes keep their separate lifetimes. Unlinking
  precedes reuse, and future scheduler-token ownership and FIFO ordering are unchanged. Storage
  costs 1,536 bytes on 64-bit native and 768 bytes on wasm32, plus queue bookkeeping.
- **Measurement tooling:** `--opt-remarks` captures the first actual optimization pipeline.
  The comparator preserves wasm modules, JS hosts and launchers together, validates tool and
  bundle hashes, and reports speedup confidence separately from regression acceptance.

## Audit and next candidates

Ranks use measured elapsed workload contribution and implementation effort, rather than remark
counts. The first inventory scan identified wasm vector addition (about 188 ms per pass), matrix
multiplication (61 ms), span splitting (61 ms) and recursion (54 ms) as the largest regions. Native
recursion, matrix multiplication and sorting led at roughly 42, 32 and 30 ms. These are workload
contributions, not an application-wide profile or an additive speedup forecast.

1. **Independent arithmetic and scans:** inconsistent wasm SIMD capabilities were a concrete
   blocker. Optimized IR and WAT distinguish actual packed instructions from scalarized vector
   helpers. Strict floating-point reductions retain their sequential order.
2. **Scheduler queues:** separate instrumentation attributes accepted enqueues, node heap
   allocations and ARC helper events. Repeated `calloc`/`free` on every enqueue/dequeue is owned
   by the C scheduler; bounded reuse needs no MIR ownership change.
3. **Strings and buffers:** equality already uses bulk comparison; wasm copying/filling already
   uses bulk memory with overlap-safe copying. Span search and serial UTF-16 hashing remain
   candidates. Calls and alias invalidation appear in first-pass LICM/vectorization remarks;
   broader `readonly`/`noalias` attributes are not justified by those messages.
4. **Collections:** list shifting/growth, map probing/span lookup/epoch clear, and set
   growth/probing/removal/clear are covered. Unmanaged clear already avoids reference traversal.
   Managed clear must preserve element release order. No new collection algorithm ships merely
   because a scalar loop or repeated load appears in remarks.
5. **Parsing:** JSON round trips, integer parsing and PCRE2 result processing are covered.
   JSON deserialization has repeated load invalidations; numeric parsing and regex also cross
   runtime-call boundaries. Specialization or buffer reuse needs a separate attributable trial.
6. **Memory and dispatch:** allocation churn, ARC locals, tree allocation/reclamation, weak
   trees, linked walks and scratch arenas cover allocation/destruction/weak/region behavior.
   Interface and captured-closure dispatch are measured separately from async polling. Atomic
   ownership operations cannot be removed through optimistic LLVM metadata.

## Correctness and artifacts

`llvm_simd_hotloops` covers zero lengths, vector-width boundaries and tails, integer wrapping,
identical array aliases, a forward-overlapping span loop, Unicode code-unit length, a strict
floating-point reduction, NaNs, infinities and signed zero. `scheduler_queue_bursts` crosses the 64-entry storage boundary in
three 257-future bursts, cancelling head, middle and tail entries before draining the queue.
Existing golden cases cover destruction order, growth, weak references and concurrent services.

Raw samples, immutable reference bundles, first-pass remarks, optimized IR, native assembly,
WAT, attribution runs and validation logs are retained under `target/hotloops/`. Diagnostic
`build.json` files record compile time and executable/module size. Compile durations are single
observations with remarks enabled, including any runtime-cache rebuilds, not statistically established wins.
Node peak RSS includes the engine and JIT; guest allocation counters exclude queue nodes, which
have their own `ready_alloc` event. ARC counters count helper events, including immortal no-ops;
row deltas also include setup and reporting between timed regions.
