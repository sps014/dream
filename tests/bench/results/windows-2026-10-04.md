The allocation-counter regression recorded below was fixed in a follow-up. See the
[counter fix measurements](windows-counter-fix-2026-10-04.md) for the current results.

Measured before Phase 7 changes, at `09d53af5`, on an Intel Core i9-13900K.
Current Dream compiler and core were rebuilt in Rust release mode; Dream programs use
`--release` (LLVM O3). C# targets .NET 10 (runtime 10.0.5, SDK 11.0.100-preview.3.26207.106).

Command: `scripts/run-microbenches.sh` under Git Bash, with the pinned
MSVC-compatible LLVM 22.1.8 clang and the release core DLL on PATH.
One warmup process, five measured processes, five passes each. Times are median ns/op;
spread is `(max-min)/median` of per-process medians, not a confidence interval.
Zero values cannot support a speedup claim. Rows above 15% spread need a repeat
measurement before interpreting a performance regression. This is a single-machine

Allocation-heavy cases show measurable regressions in this run: alloc_churn +102.8%,
arc_locals +89.9%, JSON serialization +20.8%, JSON deserialization +27.5%, and weak_tree
+14.4%. Compute cases are broadly similar. The pattern is consistent with the new atomic
read-modify-write updates, but sequential runs do not isolate causality. Counter updates
remain enabled for accurate diagnostics; this change does not claim a runtime speedup.
